## 四、卡住的点（最重要）

**卡片投递的消息，她读不到。**

证据（用户亲手点"立即执行"，06:45:51）：

```
06:45:51 agent/inbox/spliced target: next-turn [含收账]
06:45:51 turn/start                            ← 同一毫秒
06:45:51 user/message src:humanity-evolution   ← 我们注入的，在这一轮里
06:45:51 session-log-deepseek/delivery-accepted ← 卡片消息这时才被接受
06:45:51 她回话 → turn/end completed
```

- 卡片消息被排进 **`next-turn` 队列**，而这一轮已经开始读了 → 抢跑，之后没有下一轮 → **永远躺在队列里**；
- 面板显示"投递成功"（`lastDelivery` 有值），但**"投递成功" ≠ "她看到"**；
- 定时到点、`run`、手动点击，三条路都一样（05:50、05:52 那两次成功是碰巧没抢跑）；
- 对照组：同一轮里 **`user/message src:humanity-evolution`（插件注入）稳定出现**，她读到了。

## 七、坑与经验（别再踩）

- 插件日志进不了 `docker logs`：诊断要写进 `humanity.json` 的状态字段（`lastError` / `lastSettleError`）。
- `tools.definitions()` **必须传 agent** 作为 scope，否则返回全局工具（会冒出 `univer_*`、`team_task_*`）。
- 手工改 `humanity.json` 逼她醒会引入假象：状态与调度器会不一致，测试要走真实路径。
- `docker restart` 后 `arm` 会重跑：任何"只做一次"的行为都要在状态里留标记（如 `collectAt`）。
- 会话文件是 zstd 压缩的 jsonl：`/data/dsh/sessions/--data-dsh-humanity-room--/<session-id>/session.v4.jsonl.zstd`。
